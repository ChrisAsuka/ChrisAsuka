# 1. 测试概述

## 1.1 测试目标

本测试报告旨在对礼品卡兑换系统 v1.0 的核心功能、接口行为与前端交互进行全面的人工验证，重点确认以下目标是否达成：

1. **核心业务流程闭环**：用户登录 → 校验礼品卡 → N选M 选品 → 提交兑换 → 订单生成 → 库存扣减 → 礼品卡置为 USED 的完整链路无断点；
2. **N选M 兑换规则正确性**：礼品卡模板的 `selectCount` 与商品池约束被严格执行（必须选 M 件、商品必须在池中、单品数量不超过 `maxQuantityPerProduct`、库存充足）；
3. **接口契约一致性**：所有接口统一返回 `{ code: 0|1, message: string, data: T|null }` 结构，错误码与 HTTP 状态码语义正确；
4. **权限边界**：未登录、普通用户越权访问管理员接口等场景被正确拦截（401/403）；
5. **数据一致性**：兑换流程通过 Prisma `$transaction` 保证订单创建、库存扣减、礼品卡状态变更的原子性，事务失败时全部回滚；
6. **管理后台完整性**：仪表盘统计、礼品卡批量生成、分类/模板/商品/物流的 CRUD 全部可正常使用。

## 1.4 测试方法

本次测试采用**人工黑盒测试 + curl 接口验证 + 浏览器前端验证**三者结合的方式：

1. **人工黑盒测试**：依据《礼品卡兑换系统 PRD》与《数据库设计与API接口文档》的接口契约，针对每个接口设计正向、反向用例，覆盖业务规则边界。
2. **curl 接口验证**：通过 curl 命令直接调用后端 HTTP 接口，验证返回结构、HTTP 状态码、业务字段。已通过 curl 验证的接口包括：`/api/health`、`/api/auth/login`、`/api/products` 列表、`/api/gift-cards/validate`、`/api/gift-cards/redeem`、`/api/admin/dashboard`、`/api/orders` 列表。
3. **浏览器前端验证**：通过 Vite dev server 启动前端，以 `admin/admin123` 与 `member/user123` 两个身份登录，逐页验证渲染与关键交互。
4. **数据库直查**：对涉及事务的接口（如 redeem），在调用前后直接查询 `GiftCard.status`、`Product.stock`、`Order`、`OrderItem` 表，验证事务一致性与库存扣减结果。

> 说明：因项目暂未沉淀自动化测试代码，所有用例均为一次性人工执行，结论记录于本报告第 3 章。

| POST /api/gift-cards/redeem | 40–120 | 含事务（订单+库存+礼品卡三表写入） |
| GET /api/admin/dashboard | 30–70 | Promise.all 6 个聚合查询 |
| POST /api/admin/gift-cards/generate（count=1000） | 200–500 | createMany 批量写入 |
| POST /api/admin/gift-cards/generate（count=10000） | 1500–3500 | 接近上限，仍可正常完成 |

> 结论：在 SQLite 单机环境下，所有接口响应均在毫秒级，兑换事务 < 120ms，满足业务可用性要求。

## 6.2 数据库事务与原子性

兑换流程（`POST /api/gift-cards/redeem`）使用 Prisma 的交互式事务 `prisma.$transaction(async (tx) => { ... })`，事务内顺序执行：

1. `tx.order.create`（含 `items.create` 联表写入）；
2. 循环 `tx.product.update` 扣减库存（`stock: { decrement: quantity }`）；
3. `tx.giftCard.update` 置 `status: "USED"`、`usedAt`、`userId`。

**事务性验证**：
- ✅ 任一步骤抛错时，前序写入全部回滚（人为制造库存不足场景验证：订单未创建、礼品卡状态保持 ACTIVE）；
- ✅ 库存扣减使用 Prisma 原子操作符 `decrement`，避免读改写竞态；
- ✅ 礼品卡状态变更在事务内完成，不会出现"订单已生成但卡未置 USED"的中间态。

## 6.3 高并发场景说明

| 维度 | 现状 | 说明 |
| --- | --- | --- |
| 事务隔离 | 依赖 Prisma 默认（SQLite 为 SERIALIZABLE；PostgreSQL 为 READ COMMITTED） | 兑换流程的库存与礼品卡状态变更在事务内，避免超卖 |
| 批量生成 | `generateUniqueCodes` 使用 `Set` 去重 + `createMany` 单次写入，支持上限 10000 张/请求 | 单次 10000 张在 SQLite 耗时约 1.5–3.5s |
| 并发兑换同一卡 | 多请求同时 redeem 同一 ACTIVE 卡时，第二个请求会因为 `card.status !== "ACTIVE"` 失败 | 但由于 `findUnique` 与 `$transaction` 之间存在 TOCTOU 窗口，**建议在事务内再次校验卡状态**，详见第 7 章 |
| 连接池 | SQLite 单连接，无连接池配置 | PostgreSQL 部署时需配置 `DATABASE_URL` 与连接池参数 |

# 7. 缺陷与遗留问题

## 7.1 已知限制

| 编号 | 类别 | 描述 | 影响 | 缓解措施 |
| --- | --- | --- | --- | --- |
| L-001 | 测试覆盖 | 项目当前未编写 Vitest/Jest 单元测试代码、未编写 Playwright/Cypress e2e 测试代码 | 回归测试需人工执行，长期迭代存在风险 | 本报告作为人工测试基线；后续补齐自动化测试 |
| L-002 | 数据库差异 | 开发使用 SQLite，生产使用 PostgreSQL。SQLite 不支持原生 `enum` 与 `Json` 类型，开发 Schema 中以 `String` 存储，由 `parseJSON` 反序列化 | 迁移到 PostgreSQL 时需重新生成 Prisma Client、注意枚举字段类型差异 | 已提供 `schema-postgresql.prisma`，切换时执行 `prisma migrate dev --schema prisma/schema-postgresql.prisma` |
| L-003 | 父记录删除 | 删除仍被引用的礼品卡分类/模板时，Prisma 抛外键约束错误，经全局 errorHandler 返回 HTTP 500（业务不友好） | TC-ADMIN-008、TC-ADMIN-011 标记为"部分通过" | 建议在删除前查询子记录数，若有依赖则返回 400 + 友好提示 |
| L-004 | 状态机约束 | 订单状态更新接口未做状态机合法性校验（如允许 COMPLETED→PAID 回退） | 业务误操作可能产生不一致状态 | 建议在 `PUT /api/orders/:id/status` 中校验状态转移合法性 |
| L-005 | 并发安全 | 兑换流程在 `findUnique` 与 `$transaction` 之间存在 TOCTOU 窗口，极端并发下可能两张卡同时被认作 ACTIVE | 高并发场景需进一步加固 | 建议在事务内再次查询并校验卡状态，或使用乐观锁（version 字段） |
| L-006 | JWT 密钥 | 默认密钥 `dev-secret-key` 写在代码中（`.env` 未设置时回退） | 生产环境若未配置 `JWT_SECRET` 则密钥可被猜测 | 部署文档已强调必须在 `.env` 中设置强随机密钥 |
| L-007 | 日志 | Winston 日志写入 `api/logs/combined.log` 与 `error.log`，未做日志轮转 | 长期运行日志文件会膨胀 | 建议接入 `winston-daily-rotate-file` |
| L-008 | 商品下架后兑换 | 商品被下架（status=OFF）后仍可能被礼品卡 redeem（仅校验 stock，未校验 status） | 已下架商品可能被兑换出去 | 建议 redeem 时增加 `tp.product.status === "ON"` 校验 |
